### 1.4 로그인 유저

JWT 필터가 아래 객체를 `SecurityContext`에 넣습니다. 컨트롤러에서는 이 객체만 받습니다.

```java
public record LoginUser(Long id, Role role) {}

@PostMapping("/api/auctions/{id}/bids")
public ApiResponse<BidResponse> bid(@AuthenticationPrincipal LoginUser loginUser, ...) { ... }
```

- URL 접근 권한(`/api/admin/**`는 ADMIN)은 `SecurityConfig`에서 막습니다.
- "내 경매인가", "거래 당사자인가"는 각 서비스에서 검사합니다.

### 1.5 시간과 금액

- **현재 시각은 `Clock` 빈으로 얻습니다**: `LocalDateTime.now(clock)`. 마감 연장, 스케줄러, R-17 테스트에서 시간을 고정하려면 필요합니다. `LocalDateTime.now()`를 직접 부르지 마세요.
- 시간대는 `Asia/Seoul`, JSON은 `"2026-11-24T10:00:00"` 형식입니다.
- 금액은 모두 `long`(원)입니다. 비율 계산은 `BigDecimal`로만 합니다(3.2절).

### 1.6 정책 설정값 바인딩

```java
@ConfigurationProperties(prefix = "auction")
public record AuctionPolicyProperties(Fee fee, BidUnit bidUnit, Extension extension, TradePolicy trade, PointPolicy point) {
    public record Fee(List<FeeTier> tiers) {}
    public record FeeTier(Long maxPrice, BigDecimal rate) {}     // maxPrice null = 상한 없음
    public record BidUnit(List<BidUnitTier> tiers) {}
    public record BidUnitTier(Long maxPrice, long unit) {}
    public record Extension(boolean enabled, int triggerMinutes, int extendMinutes) {}
    public record TradePolicy(int shipDeadlineDays, int autoConfirmDays) {}   // 엔티티 Trade와 이름이 겹치지 않게
    public record PointPolicy(long maxChargeAmount) {}
}
```

- 구간은 `maxPrice` 오름차순이고, `maxPrice`는 **이하**(경계 포함)입니다. 예를 들어 현재가가 9,999원이면 단위는 500원이고, 10,000원이면 1,000원입니다.
- 마지막 구간의 `maxPrice`는 반드시 `null`이어야 합니다. 애플리케이션이 뜰 때 이 조건을 검증합니다.

## 2. 포인트 서비스 (포인트 → 입찰·경매·거래)

### 2.1 인터페이스

```java
public interface PointService {

    /** 테스트용 충전. 자체 트랜잭션. CHARGE. (R-23) */
    void charge(Long userId, long amount);

    // ---- 아래는 모두 호출하는 쪽의 트랜잭션 안에서만 부릅니다 (propagation = MANDATORY) ----

    /**
     * 입찰 성공 시 홀딩. 새 입찰자 available → locked (BID_LOCK)
     * prevBidderId가 있으면 같은 호출 안에서 이전 최고 입찰자 locked → available (BID_UNLOCK)
     * 사용 가능 포인트가 부족하면 BALANCE_INSUFFICIENT. (R-14, R-20, R-21)
     */
    void lockForBid(Long auctionId, Long bidderId, long amount,
                    @Nullable Long prevBidderId, long prevAmount);

    /** 운영자 경매 강제 취소 시 최고 입찰자 홀딩 해제. BID_UNLOCK. (R-61) */
    void unlockBid(Long auctionId, Long userId, long amount);

    /**
     * 구매확정. 구매자 locked 차감(PURCHASE) + 판매자 available 증가(SETTLE)
     * 수수료(price - settleAmount)는 아무에게도 가지 않습니다. 플랫폼 수익입니다. (R-53)
     */
    void confirmPurchase(Long tradeId, Long buyerId, long price, Long sellerId, long settleAmount);

    /** 거래 취소 환불. 구매자 locked → available (REFUND). (R-55, R-56) */
    void refund(Long tradeId, Long buyerId, long amount);
}
```

### 2.2 약속

| 항목 | 내용 |
| --- | --- |
| 잔액 변경 | `User.availableBalance`와 `lockedBalance`는 **PointService만** 바꿉니다. User 엔티티의 잔액 변경 메서드는 포인트 담당이 작성하고, 다른 곳에서는 호출하지 않습니다. |
| 유저 락 | PointService 안에서 대상 유저들을 `PESSIMISTIC_WRITE`로 **id 오름차순** 조회합니다. 호출하는 쪽은 유저 락을 따로 걸지 않습니다. 락 순서가 한곳에서 정해지므로 데드락이 생기지 않습니다. |
| 내역 | 잔액을 바꿀 때마다 `BalanceHistory`를 한 건 남깁니다. 변동 후 잔액(`availableAfter`, `lockedAfter`)도 함께 기록합니다. |
| 참조 | `refType`은 `AUCTION`(BID_LOCK, BID_UNLOCK), `TRADE`(PURCHASE, SETTLE, REFUND), `null`(CHARGE)입니다. `refId`에는 해당 id를 넣습니다. |
| 내부 불일치 | 묶인 포인트가 차감할 금액보다 적으면 코드 버그입니다. `IllegalStateException`을 던져 500 응답과 롤백으로 처리합니다. 사용자 에러코드로 바꾸지 않습니다. |

### 2.3 금액 흐름 예시

시작가 10,000원, 즉시구매가 50,000원인 경매에서 A가 12,000원, B가 15,000원에 입찰하고 B가 낙찰된 뒤 구매확정한 경우입니다. 수수료율은 5%입니다.

| 단계 | 호출 | A (가용 / 묶임) | B (가용 / 묶임) | 판매자 가용 |
| --- | --- | --- | --- | --- |
| 시작 | | 100,000 / 0 | 100,000 / 0 | 0 |
| A 입찰 12,000 | `lockForBid(a, A, 12000, null, 0)` | 88,000 / 12,000 | 100,000 / 0 | 0 |
| B 입찰 15,000 | `lockForBid(a, B, 15000, A, 12000)` | 100,000 / 0 | 85,000 / 15,000 | 0 |
| 마감, 거래 생성 | (포인트 변동 없음) | | 85,000 / 15,000 | 0 |
| 구매확정 | `confirmPurchase(t, B, 15000, S, 14250)` | | 85,000 / 0 | 14,250 |

public interface FeeCalculator {

> **`double`을 쓰면 안 되는 이유**: `100000 * 0.03`은 double로 `2999.9999…`가 나올 수 있고, 이를 버림하면 2,999원이 됩니다. 반드시 `BigDecimal`로 계산하세요. 경계 금액 테스트를 꼭 넣으세요.

## 4. 경매 엔티티 메서드 (경매 ↔ 입찰)

`Auction`은 경매 담당 소유입니다. 다만 입찰과 관련된 메서드는 입찰 담당이 구현합니다. Day 1 엔티티 머지 때 시그니처를 함께 넣습니다.

| 메서드 | 구현 | 내용 |
| --- | --- | --- |
| `boolean isOpenAt(LocalDateTime now)` | 입찰 | `status == ACTIVE && now < endAt` (R-17) |
| `long minimumBid(long bidUnit)` | 입찰 | 입찰 0건이면 `startPrice`, 아니면 `currentPrice + bidUnit` (R-12) |
| `boolean canBuyNow()` | 입찰 | `buyNowPrice != null && currentPrice < buyNowPrice` (R-03, R-45) |
| `void applyBid(User bidder, long amount, LocalDateTime now)` | 입찰 | 현재가·최고 입찰자 갱신, 입찰 수 +1, 마감 연장 판단 (R-30) |
| `void markBoughtNow()` | 입찰 | ACTIVE → BOUGHT_NOW |
| `void close()` | 경매 | 스케줄러에서 호출. 입찰이 있으면 SOLD, 없으면 FAILED (R-41) |
| `void cancel()` | 경매 | ACTIVE → CANCELED (판매자 또는 운영자) |
| `boolean isEditable()` | 경매 | `status == ACTIVE && bidCount == 0` (R-06) |

**마감 연장 계산 (R-30)**

```java
if (extendEnabled && !now.isBefore(endAt.minusMinutes(extendTriggerMinutes))) {
    LocalDateTime extended = now.plusMinutes(extendMinutes);
    if (extended.isAfter(endAt)) {    // 연장 시간이 감지 구간보다 짧게 설정돼도 마감이 앞당겨지지 않도록
        endAt = extended;
        extendCount++;
    }
}
```

**즉시구매 처리 (R-40, R-43, R-44)**

입찰가가 즉시구매가 이상이면, 입찰 서비스가 처리 금액을 **즉시구매가로 바꿔서** 진행합니다. `lockForBid`, `applyBid`, Bid 저장 모두 즉시구매가로 합니다. 처음부터 즉시구매가만큼만 묶기 때문에 R-43의 "차액 해제"가 따로 필요 없습니다.

## 5. 거래 생성 (거래 → 입찰·경매)

```java
public interface TradeService {
    /**
     * 거래를 만듭니다. 호출하는 쪽의 트랜잭션 안에서만 부릅니다 (MANDATORY).
     * - 수수료: FeeCalculator로 계산해 스냅샷 (R-54)
     * - 배송지: buyer.getAddress().copy()로 복사 (R-57)
     * - status = PAID, tradedAt = now, shipDeadlineAt = now + shipDeadlineDays
     * - TradeCreatedEvent 발행
     * 포인트는 움직이지 않습니다. 구매자의 묶인 포인트가 그대로 에스크로 역할을 합니다. (R-42)
     */
    Trade createTrade(Auction auction, User buyer, TradeType type, long price);
}
```

| 호출하는 곳 | type | price |
| --- | --- | --- |
| 입찰 서비스 (즉시구매) | `BUY_NOW` | `buyNowPrice` |
| 경매 종료 스케줄러 (SOLD) | `BID_WIN` | `currentPrice` |

`Address`는 setter 없는 불변 값 타입이고, `copy()`로 새 인스턴스를 만듭니다. 같은 임베디드 인스턴스를 두 엔티티가 공유하면 JPA에서 문제가 생기므로 반드시 복사합니다.

## 6. 도메인 이벤트 (각 도메인 → 알림)

### 6.1 이벤트 목록

모든 이벤트는 Java `record`이고, 발행하는 도메인의 `event` 패키지에 둡니다. 알림 담당이 다시 조회하지 않아도 되도록 메시지에 쓸 값(제목 등)을 함께 담습니다. 알림 문구는 알림 담당이 만듭니다.

```java
// 입찰
public record OutbidEvent(Long auctionId, String auctionTitle, Long userId, long newPrice) {}

// 경매
public record AuctionFailedEvent(Long auctionId, String auctionTitle, Long sellerId) {}
public record AuctionCanceledEvent(Long auctionId, String auctionTitle, Long sellerId,
                                   @Nullable Long highestBidderId, boolean byAdmin) {}

// 거래
public record TradeCreatedEvent(Long tradeId, Long auctionId, String auctionTitle,
                                Long buyerId, Long sellerId, TradeType type, long price) {}
public record TradeShippedEvent(Long tradeId, String auctionTitle, Long buyerId, String trackingNumber) {}
public record TradeConfirmSoonEvent(Long tradeId, String auctionTitle, Long buyerId, LocalDateTime autoConfirmAt) {}
public record TradeCanceledEvent(Long tradeId, String auctionTitle, Long buyerId, Long sellerId,
                                 CancelReason reason) {}
```

| 이벤트 | 발행 위치 | 알림 타입 → 받는 사람 |
| --- | --- | --- |
| `OutbidEvent` | 입찰 성공 시, 이전 최고 입찰자가 있을 때 (즉시구매 포함) | OUTBID → 이전 최고 입찰자 |
| `TradeCreatedEvent` | `createTrade` 안 | AUCTION_WON → 구매자, AUCTION_SOLD → 판매자 |
| `AuctionFailedEvent` | 경매 종료 스케줄러 (FAILED) | AUCTION_FAILED → 판매자 |
| `AuctionCanceledEvent` | 판매자 취소, 운영자 강제 취소 | 운영자 취소일 때만 AUCTION_CANCELED → 판매자, 최고 입찰자(있을 때). 판매자 본인 취소는 알림 없음 |
| `TradeShippedEvent` | 송장 입력 | SHIPPED → 구매자 |
| `TradeConfirmSoonEvent` | 확정 임박 스케줄러 (`confirmSoonNotified == false`인 거래만, 발행 후 `true`로 바꿈) | CONFIRM_SOON → 구매자 |
| `TradeCanceledEvent` | 송장 기한 스케줄러, 운영자 취소 | TRADE_CANCELED → 구매자, 판매자 |

> 낙찰과 즉시구매는 둘 다 `createTrade`를 거치므로, 알림 이벤트를 한곳에서만 발행하면 됩니다.

### 6.2 발행·구독 규칙

```java
// 발행 (각 도메인 서비스, @Transactional 메서드 안)
eventPublisher.publishEvent(new OutbidEvent(...));

// 구독 (알림 담당)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void handle(OutbidEvent e) { ... }
```

1. **`REQUIRES_NEW`가 필요합니다.** AFTER_COMMIT 시점에는 원래 트랜잭션이 이미 끝났기 때문에, 새 트랜잭션 없이 저장하면 알림이 DB에 들어가지 않습니다.
2. **이벤트는 트랜잭션 안에서 발행해야 합니다.** 트랜잭션 밖에서 발행하면 `@TransactionalEventListener`가 **아무 오류 없이** 이벤트를 무시합니다. 스케줄러가 자주 실수하는 곳입니다.
3. 알림 저장이 실패하면 로그만 남깁니다. 원래 입찰이나 거래에는 영향을 주지 않습니다.
4. 입찰이나 거래가 롤백되면 이벤트도 사라집니다. 실패한 입찰에 대해 알림이 가지 않습니다.

## 7. 동시성·스케줄러 약속

| 항목 | 약속 |
| --- | --- |
| 입찰 충돌 | Auction의 `@Version` 충돌(`OptimisticLockingFailureException`)이 나면 서버에서 재시도하지 않고 `BID_CONFLICT`(409)로 응답합니다. 클라이언트가 최신 현재가를 보고 다시 입찰합니다. (R-16) |
| version 증가 | 입찰, 즉시구매, 종료, 취소, 수정 모두 Auction을 갱신하므로 version이 올라갑니다. 입찰과 스케줄러 종료가 겹치면 한쪽만 성공합니다. |
| 스케줄러 트랜잭션 | 대상을 조회한 뒤 **한 건씩 별도 트랜잭션**으로 처리합니다. 한 건이 실패해도 나머지는 처리되고, 실패한 건은 다음 주기에 다시 처리됩니다. |
| 스케줄러와 이벤트 | 한 건을 처리하는 메서드에 `@Transactional`을 붙이고, 그 안에서 이벤트를 발행합니다(6.2절 2번). |

## 8. 결정 사항

계약을 정리하면서 발견한 빈틈과 결정입니다. 도메인 문서와 기술서에도 반영했습니다.

| # | 질문 | 결정 | 이유 |
| --- | --- | --- | --- |
| 1 | 운영자가 경매를 강제 취소하면 최고 입찰자에게 알릴까? | `AUCTION_CANCELED` 알림 타입을 추가해 판매자와 최고 입찰자에게 보냄 | 포인트가 풀렸는데 이유를 모르면 혼란스러움. 이벤트는 이미 있으므로 enum 값 하나만 늘리면 됨 |
| 2 | 확정 임박 알림이 매시간 중복으로 가지 않게 하려면? | Trade에 `confirmSoonNotified`(boolean) 필드를 추가 | 시간 범위로만 거르면 스케줄러가 늦거나 겹칠 때 누락·중복이 생김 |
| 3 | 현재 최고 입찰자도 즉시구매를 할 수 있나? | 막음 (`ALREADY_HIGHEST_BIDDER`) | 허용하면 이미 묶인 금액과의 차액만 추가로 묶는 별도 흐름이 필요함 |
| 4 | 입찰 충돌 시 서버가 재시도할까? | 재시도 없이 409 응답 (7장) | 재시도하면 입찰가 검증을 다시 해야 하고, 사용자가 의도하지 않은 금액으로 입찰될 수 있음 |
| 5 | 즉시구매가보다 높게 입찰하면 얼마를 묶을까? | 처음부터 즉시구매가만큼만 묶음 (4장) | 묶었다가 차액을 푸는 것보다 단순하고, 내역도 한 줄로 끝남 |
