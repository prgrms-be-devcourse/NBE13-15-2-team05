> 기준: [프로젝트_기술서.md](프로젝트_기술서.md), [모듈_계약서.md](모듈_계약서.md)
> 자기 파트만 읽어도 무엇을, 어떤 순서로, 언제까지 해야 하는지 알 수 있게 정리했습니다.

## 0. 모두 공통

### 시작하는 법

1. 저장소를 클론하고 Docker Desktop을 켭니다.
2. `./gradlew bootRun`으로 앱이 뜨는지 확인합니다. Swagger: http://localhost:8080/swagger-ui.html
3. `dev`에서 `feature/{이슈번호}-{기능}` 브랜치를 따서 작업하고, `dev`로 PR을 올립니다.
4. 내 할 일 찾기: `grep -rn "TODO(포인트)" src/main`. 괄호 안에 내 담당 이름을 넣습니다.

### 모두가 하는 일

- **내 엔티티의 생성 메서드 작성**: 지금 엔티티에는 필드만 있고 생성자가 없습니다. 정적 팩토리(`Auction.create(...)`)나 생성자를 각자 추가합니다.
- **DTO와 컨트롤러**: `dto`, `controller` 패키지에 직접 만듭니다. 응답은 항상 `ApiResponse`로 감쌉니다.
- **에러**: `throw new BusinessException(BidErrorCode.BID_TOO_LOW)`. 에러코드가 더 필요하면 내 도메인 enum에 추가합니다.
- **시간**: `LocalDateTime.now(clock)`만 씁니다.
- **PR**: 제목이나 본문에 관련 규칙 번호(R-xx)를 적습니다.

### 계약 파일은 함부로 바꾸지 않습니다

아래 파일의 **메서드 시그니처**는 다른 사람이 이미 호출하고 있습니다. 바꿔야 하면 먼저 팀 채널에 공유합니다.

`PointService`, `FeeCalculator`, `BidUnitPolicy`, `TradeService`, `Auction`의 입찰·종료 메서드, 이벤트 record 7개

### 다른 사람 코드가 아직 없을 때

계약 인터페이스는 이미 있으므로 **호출하는 코드는 지금 바로 짤 수 있습니다**. 실행해 보려면 테스트에서 Mockito로 가짜 구현을 넣습니다.

```java
@MockitoBean PointService pointService;   // 포인트 구현 전에도 입찰 로직 테스트 가능
```

## 1. 누가 누구를 기다리나

먼저 끝내야 다른 사람이 막히지 않는 것들입니다. **굵은 날짜를 꼭 지켜 주세요.**

| 무엇 | 담당 | 기다리는 사람 | 목표 |
| --- | --- | --- | --- |
| 회원가입·로그인·JWT 필터 | 회원·공통 | 전원 (로그인해야 API 테스트 가능) | **3일차** |
| 테스트 데이터 (유저, 운영자, 카테고리) | 회원·공통 | 전원 | **3일차** |
| 카테고리 등록, 경매 등록 | 경매 | 입찰 | **4일차** |
| `charge`, `lockForBid` | 포인트 | 입찰 | **4일차** |
| `FeeCalculator` | 포인트 | 거래 | **5일차** |
| `createTrade` | 거래 | 입찰(즉시구매), 경매(종료 스케줄러) | **6일차** |
| `confirmPurchase`, `refund`, `unlockBid` | 포인트 | 거래, 경매 | **6일차** |
| 이벤트 발행 | 입찰, 경매, 거래 | 알림 | 7일차 |

```
회원(JWT) ──▶ 모두
경매(등록) ──▶ 입찰 ──▶ 거래(createTrade) ◀── 경매(종료 스케줄러)
포인트(lock) ─▶ 입찰      포인트(fee, confirm, refund) ─▶ 거래
입찰·경매·거래(이벤트) ──▶ 알림
```

## 2. 팀장 — 입찰

**한 줄 역할**: 이 프로젝트에서 가장 어려운 부분입니다. 동시에 들어오는 입찰을 정확하게 처리하고, 포인트 홀딩과 마감 연장, 즉시구매를 한 트랜잭션으로 묶습니다.

### 담당 범위

| 구분 | 내용 |
| --- | --- |
| API (5) | `POST /api/auctions/{id}/bids` 입찰 · `POST /api/auctions/{id}/buy-now` 즉시구매 · `GET /api/auctions/{id}/bids` 입찰 내역 · `GET /api/users/me/bids` 내 입찰 목록 · `GET /api/admin/auctions/{id}/bids` 실제 입찰자 포함 내역(운영자) |
| 이미 있는 TODO | `Auction`의 `isOpenAt`, `minimumBid`, `canBuyNow`, `applyBid`, `markBoughtNow` · `BidUnitPolicyImpl` |
| 직접 만들 것 | `BidService`, `BidController`, DTO, `Bid` 생성 메서드 |
| 발행할 이벤트 | `OutbidEvent` |
| 규칙 | R-10 ~ R-19, R-30, R-31, R-40, R-43 ~ R-45 |

### 순서

1. **(1~3일차)** `BidUnitPolicyImpl`과 `Auction`의 입찰 메서드 5개를 단위 테스트와 함께 구현합니다. DB 없이 테스트할 수 있습니다.
2. **(3~5일차)** 입찰 API: 기술서 9.1의 8단계를 그대로 따릅니다. 포인트는 `pointService.lockForBid(...)`만 호출합니다.
3. **(5일차)** 입찰 내역과 내 입찰 목록 API. 내역은 금액과 시각만 보여주고, 본인 입찰에는 표시를 붙입니다(R-18).
4. **(6일차)** 즉시구매: 입찰가가 즉시구매가 이상이면 처리 금액을 즉시구매가로 바꾸고, `markBoughtNow()` 후 `tradeService.createTrade(..., BUY_NOW, buyNowPrice)`를 부릅니다.
5. **(6~7일차)** 커밋 후 `OutbidEvent` 발행, version 충돌 시 `BID_CONFLICT`(409) 응답.
6. **(8~9일차)** 동시성 테스트: Testcontainers에서 100명이 동시에 입찰해도 현재가, 최고 입찰자, 묶인 포인트 합계가 맞는지 확인합니다.

### 꼭 넣을 테스트

- 마감 직전 입찰 시 연장되는지, 연장 시간이 감지 구간보다 짧아도 마감이 앞당겨지지 않는지
- 입찰 단위 경계: 현재가 9,999원 → 500원 단위, 10,000원 → 1,000원 단위
- 마감 시각이 지난 입찰이 상태와 관계없이 거절되는지 (R-17)
- 동시 입찰 100건

### 주의

- 유저 락은 직접 걸지 않습니다. `PointService` 안에서 겁니다.
- `OptimisticLockingFailureException`은 커밋 시점에 터질 수 있습니다. 서비스 메서드 밖(컨트롤러 또는 예외 처리기)에서 잡아 409로 바꿉니다.

## 3. 포인트·정산

**한 줄 역할**: 돈을 다루는 유일한 곳입니다. 잔액과 내역이 절대 어긋나지 않게 하고, 다른 세 명이 부를 메서드를 **가장 먼저** 내놓습니다.

### 담당 범위

| 구분 | 내용 |
| --- | --- |
| API (2) | `POST /api/users/me/charge` 충전 · `GET /api/users/me/balance-histories` 변동 내역 |
| 이미 있는 TODO | `PointServiceImpl`의 5개 메서드 · `FeeCalculatorImpl` |
| 직접 만들 것 | `User`의 잔액 변경 메서드, `BalanceHistory` 생성 메서드, 컨트롤러, DTO |
| 규칙 | R-14, R-20 ~ R-23, R-53 ~ R-55 |

### 순서

1. **(1~2일차)** `User`에 잔액 변경 메서드(`charge`, `lock`, `unlock`, `deductLocked`, `addAvailable` 등)를 만듭니다. 메서드 안에서 음수가 되지 않는지 검사합니다.
2. **(3~4일차, 입찰 담당이 기다림)** `charge`, `lockForBid` 구현과 충전 API. 유저 조회는 `userRepository.findAllByIdInForUpdate(ids)`로 합니다(id 오름차순 락).
3. **(5일차, 거래 담당이 기다림)** `FeeCalculatorImpl`. 반드시 `BigDecimal`로 계산하고 원 단위 미만은 버립니다.
4. **(5~6일차)** `confirmPurchase`, `refund`, `unlockBid`.
5. **(6일차)** 변동 내역 조회 API (페이지네이션, 최신순).
6. **(8~9일차)** 정합성 테스트: 시나리오가 끝난 뒤 모든 유저의 `available + locked`가 충전 합계 − 수수료 합계와 같은지 확인합니다.

### 꼭 넣을 테스트

- 수수료 경계: 99,999원(5%) → 4,999원, 100,000원(3%) → 3,000원 (`double`로 계산하면 2,999원이 나올 수 있음)
- `lockForBid`에서 이전 입찰자 해제와 새 입찰자 홀딩이 같은 트랜잭션에서 이뤄지는지
- 사용 가능 포인트 부족 시 `BALANCE_INSUFFICIENT`이고, 아무 잔액도 바뀌지 않는지
- 모든 변동마다 `BalanceHistory`가 한 건씩, 변동 후 잔액과 함께 남는지

### 주의

- `charge`를 뺀 메서드는 `Propagation.MANDATORY`입니다. 트랜잭션 없이 부르면 예외가 납니다. 이건 의도된 동작입니다.
- 묶인 포인트가 차감할 금액보다 적으면 사용자 에러가 아니라 코드 버그입니다. `IllegalStateException`을 던집니다.

## 4. 경매 (+ 카테고리, 종료 스케줄러)

**한 줄 역할**: 경매가 등록되어 끝날 때까지의 생명주기를 맡습니다. API 수가 가장 많지만, 대부분 조회와 단순 CRUD입니다.

### 담당 범위

| 구분 | 내용 |
| --- | --- |
| API (11) | 카테고리 4개 (`GET /api/categories`, 운영자 등록·수정·삭제) · 경매 6개 (등록, 목록, 상세, 수정, 취소, 내 판매 목록) · `POST /api/admin/auctions/{id}/cancel` 운영자 강제 취소 |
| 이미 있는 TODO | `Auction`의 `close`, `cancel`, `isEditable` |
| 직접 만들 것 | `CategoryService`, `AuctionService`, 경매 종료 스케줄러, 컨트롤러, DTO, `Auction`·`AuctionImage`·`Category` 생성 메서드 |
| 발행할 이벤트 | `AuctionFailedEvent`, `AuctionCanceledEvent` |
| 규칙 | R-01 ~ R-09, R-41, R-61, R-62, R-64 |

### 순서

1. **(1~3일차)** 카테고리 CRUD. 경매가 달린 카테고리는 삭제 불가(R-64).
2. **(3~4일차, 입찰 담당이 기다림)** 경매 등록. 등록할 때 `AuctionPolicyProperties.extension()` 값을 경매에 복사합니다(R-05). `currentPrice`는 `startPrice`로, `originalEndAt`은 `endAt`으로 시작합니다.
3. **(4~5일차)** 목록(카테고리·상태 필터, 정렬, 페이지네이션), 상세(이미지, 다음 최소 입찰가 포함), 내 판매 목록.
4. **(5일차)** 수정·취소: `isEditable()`일 때만 가능(R-06).
5. **(6~7일차)** 경매 종료 스케줄러(1분): `ACTIVE`이면서 `endAt`이 지난 경매를 조회해 **한 건씩 별도 트랜잭션**으로 `close()`합니다. SOLD면 `tradeService.createTrade(..., BID_WIN, currentPrice)`, FAILED면 `AuctionFailedEvent`를 발행합니다.
6. **(8일차)** 운영자 강제 취소: `cancel()` 후 최고 입찰자가 있으면 `pointService.unlockBid(...)`, `AuctionCanceledEvent(byAdmin = true)` 발행.

### 꼭 넣을 테스트

- 등록 검증: 기간 1~14일, 100원 단위·최소 1,000원, 즉시구매가 > 시작가, 이미지 1~10장
- 등록 후 yml의 연장 설정을 바꿔도 기존 경매 값은 그대로인지
- 스케줄러: 입찰 있는 경매 → SOLD + 거래 생성, 없는 경매 → FAILED
- 스케줄러에서 한 건이 실패해도 나머지는 처리되는지

### 주의

- 목록 조회에서 N+1이 생기기 쉽습니다(판매자, 카테고리, 대표 이미지). fetch join이나 DTO 조회를 쓰세요.
- 스케줄러에서 이벤트를 트랜잭션 밖에서 발행하면 알림이 **오류 없이 사라집니다**. 한 건 처리 메서드에 `@Transactional`을 붙이고 그 안에서 발행합니다.

## 5. 거래 (+ 스케줄러 3개, 운영자 취소)

**한 줄 역할**: 낙찰 이후 송장, 구매확정, 정산, 취소까지의 흐름을 맡습니다. 시간에 따라 자동으로 처리되는 일이 많습니다.

### 담당 범위

| 구분 | 내용 |
| --- | --- |
| API (5) | `GET /api/trades?role=buyer\|seller` · `GET /api/trades/{id}` (상대 연락처 포함) · `PATCH /api/trades/{id}/tracking` 송장 입력 · `POST /api/trades/{id}/confirm` 구매확정 · `POST /api/admin/trades/{id}/cancel` 운영자 취소 |
| 이미 있는 TODO | `TradeServiceImpl.createTrade` |
| 직접 만들 것 | 거래 조회·송장·확정·취소 서비스, 스케줄러 3개, 컨트롤러, DTO, `Trade` 생성 메서드 |
| 발행할 이벤트 | `TradeCreatedEvent`, `TradeShippedEvent`, `TradeConfirmSoonEvent`, `TradeCanceledEvent` |
| 규칙 | R-42, R-50 ~ R-58 |

### 순서

1. **(1~5일차)** 거래 목록·상세 조회 API. 상세는 거래 당사자만 볼 수 있습니다.
2. **(5~6일차, 입찰·경매가 기다림)** `createTrade`: `feeCalculator.calculate(price)`로 수수료 스냅샷, `buyer.getAddress().copy()`로 배송지 복사, `shipDeadlineAt = now + 3일`, `TradeCreatedEvent` 발행.
3. **(6~7일차)** 송장 입력(PAID → SHIPPED, `autoConfirmAt = now + 7일`, `TradeShippedEvent`), 구매확정(SHIPPED → CONFIRMED, `pointService.confirmPurchase(...)`).
4. **(7~8일차)** 스케줄러 3개. 모두 **한 건씩 별도 트랜잭션**으로 처리합니다.
   - 송장 기한 초과(10분): PAID이면서 `shipDeadlineAt` 지남 → CANCELED(SHIP_TIMEOUT), `refund`, `TradeCanceledEvent`
   - 자동 구매확정(10분): SHIPPED이면서 `autoConfirmAt` 지남 → 구매확정과 같은 처리
   - 확정 임박 알림(1시간): SHIPPED, `autoConfirmAt`까지 24시간 이내, `confirmSoonNotified == false` → `TradeConfirmSoonEvent`, 플래그를 true로
5. **(8일차)** 운영자 취소: 구매확정 전(PAID, SHIPPED)만 가능, `refund`, `TradeCanceledEvent`.

### 꼭 넣을 테스트

- 상태 전이: PAID에서 확정 시도, CONFIRMED에서 취소 시도 → `TRADE_INVALID_STATUS`
- 거래 성립 후 구매자가 배송지를 바꿔도 거래의 배송지는 그대로인지 (R-57)
- `Clock`을 고정해서 스케줄러 3개의 기한 경계를 확인
- 확정 임박 알림이 두 번 가지 않는지

## 6. 회원·공통·알림

**한 줄 역할**: 모두가 쓰는 기반을 만듭니다. 특히 **로그인이 되어야 다른 사람이 API를 테스트할 수 있으므로** 3일차까지가 가장 중요합니다.

### 담당 범위

| 구분 | 내용 |
| --- | --- |
| API (6) | `POST /api/auth/signup` · `POST /api/auth/login` · `GET /api/users/me` · `PATCH /api/users/me` (닉네임, 연락처, 기본 배송지) · `GET /api/notifications` · `PATCH /api/notifications/{id}/read` |
| 이미 있는 TODO | `JwtTokenProvider`, `JwtAuthenticationFilter`, `NotificationEventListener` |
| 직접 만들 것 | JWT 라이브러리 추가와 설정, `UserService`, `NotificationService`, 테스트 데이터, `User`·`Notification` 생성 메서드 |
| 규칙 | R-19(배송지 등록), R-63, R-65, R-66 |

### 순서

1. **(1~3일차, 전원이 기다림)**
   - JWT 라이브러리를 고르고(`jjwt` 추천) `build.gradle`과 `application.yml`에 추가합니다. 시크릿은 환경변수로 받습니다.
   - `JwtTokenProvider`, `JwtAuthenticationFilter` 구현. 권한은 `ROLE_USER`, `ROLE_ADMIN`.
   - 회원가입(이메일·닉네임 중복 검사), 로그인.
   - **테스트 데이터**: 로컬 프로필에서만 도는 초기화 코드로 일반 유저 몇 명(포인트 충전, 기본 배송지 포함), **운영자 계정 1개**, 카테고리 몇 개를 넣습니다. 운영자 가입 API는 없으므로 여기서만 만들 수 있습니다.
2. **(4~5일차)** 내 정보 조회·수정. 묶인 포인트가 있으면 배송지를 비울 수 없습니다(R-66).
3. **(6~7일차)** 알림 리스너: 계약서 6.1 표대로 이벤트 7종을 받아 `Notification`을 저장합니다. 문구는 여기서 만듭니다.
4. **(7일차)** 알림 목록(최신순, 페이지네이션), 읽음 처리. 남의 알림은 404로 응답합니다.
5. **(8~9일차)** Swagger 정리(로그인 후 Authorize 버튼으로 토큰 넣기), 공통 예외 누락 확인.

### 꼭 넣을 테스트

- 토큰 없음 → 401, 일반 유저가 `/api/admin/**` 호출 → 403, 응답이 `ApiResponse` 형식인지
- 입찰이 롤백되면 알림도 생기지 않는지
- 알림 저장이 실패해도 원래 입찰·거래는 커밋되는지

### 주의

- 리스너에는 `@TransactionalEventListener(AFTER_COMMIT)`와 `@Transactional(REQUIRES_NEW)`가 둘 다 필요합니다. 하나라도 빠지면 알림이 저장되지 않습니다.

## 7. 10일차 시연 시나리오

모든 담당자의 작업이 합쳐졌을 때 이 흐름이 끝까지 돌아야 합니다. 8~9일차에 다 같이 확인합니다.

1. 판매자 A, 구매자 B·C 가입 → 로그인 → 포인트 충전 → 기본 배송지 등록
2. A가 경매 등록 (마감 몇 분 뒤로 짧게)
3. B 입찰 → C가 더 높게 입찰 → B의 포인트가 풀리고 B에게 OUTBID 알림
4. 마감 직전 B 재입찰 → 마감 연장 확인
5. 마감 → 스케줄러가 SOLD 처리 → 거래 생성, 낙찰·판매 알림
6. A 송장 입력 → B 구매확정 → A에게 수수료를 뺀 금액 정산
7. 별도 경매로 즉시구매, 송장 기한 초과 자동취소, 운영자 강제 취소도 한 번씩 확인
